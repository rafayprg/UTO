In modern distributed web architectures, microservices, and Single-Page Applications (SPAs), JSON Web Tokens (JWT, formalized in RFC 7519) serve as the dominant standard for stateless identity assertion and API authorization.

Unlike legacy session architectures that require database or Redis lookups for every incoming HTTP request, a JWT carries its own cryptographic verification envelope, allowing backend servers to validate user permissions statelessly at scale.

## The Tripartite Architecture of a JWT

A JSON Web Token is a compact string separated by two period (`.`) characters:

```text
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiIxMjM0NTY3ODkwIiwibmFtZSI6IkFsZXggTW9yZ2FuIiwiaWF0IjoxNTE2MjM5MDIyfQ.SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c
```

Each of the three segments is encoded independently using URL-safe Base64:

### 1. The Header (Algorithm & Token Type)
The header specifies the cryptographic metadata necessary to parse and verify the signature:

```json
{
  "alg": "HS256",
  "typ": "JWT"
}
```
Common signing algorithms include symmetric HMAC algorithms (`HS256`, `HS512`) and asymmetric public-private key pairs (`RS256`, `ES256`).

### 2. The Payload (Claims & Identity Data)
The payload contains the **claims**—statements regarding an entity (typically the authenticated user) and contextual metadata:

```json
{
  "sub": "usr_948291a0",
  "name": "Alex Morgan",
  "role": "admin",
  "iss": "https://auth.localtools.com",
  "exp": 1732204800,
  "iat": 1732161600
}
```

RFC 7519 defines several standard reserved claims:
- `iss` (Issuer): The identity provider that issued the token.
- `sub` (Subject): The unique user ID or account identifier.
- `exp` (Expiration Time): Unix epoch timestamp after which the token is invalid.
- `nbf` (Not Before): Unix epoch timestamp before which the token cannot be accepted.
- `iat` (Issued At): Timestamp when the token was created.

### 3. The Signature (Tamper-Proof Guarantee)
The signature is generated by combining the encoded header, the encoded payload, and a secret cryptographic key:

```text
HMACSHA256(
  base64UrlEncode(header) + "." + base64UrlEncode(payload),
  secret_key
)
```

If an attacker modifies a single character in the payload (for example, altering `"role": "user"` to `"role": "admin"`), the resulting signature calculation will fail to match, causing backend API gateways to reject the request instantly.

## Critical Security Anti-Patterns to Avoid

While JWT is a robust standard, improper implementation leads to severe security breaches:

### 1. Confusing Encoding with Encryption
Base64URL encoding is **not** encryption. Never store private API keys, social security numbers, or internal database connection strings in a JWT payload. If confidentiality is required, use **JSON Web Encryption (JWE)** or keep data server-side.

### 2. The Algorithm Confusion Attack
When using asymmetric algorithms like `RS256`, the authentication server signs tokens using a private RSA key, while client services verify using the public RSA key. If a backend library naively trusts the header `alg` field without strict validation, an attacker can re-sign a token using the server's public key as an HMAC symmetric secret (`HS256`), tricking the server into accepting forged permissions.

### 3. Lack of Expiration Controls
Stateless JWTs cannot be easily revoked without introducing a server-side revocation list or Redis blacklist. Always configure short token lifespans (e.g., 10 to 15 minutes) paired with rotating refresh tokens.
